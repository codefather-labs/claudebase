**Feature slug:** `pty-transport`
**Owner:** оператор (Vladislav) / Mira (orchestrator)
**Date drafted:** 2026-08-16
**Статус:** Слайсы 0–8 (кроме 4, отменённого), 10, 11 и 12 ВЫПОЛНЕНЫ (Слайс 4 отменён Слайсом 10) и проверены вживую 2026-08-16 (`docs/qa/evidence/pty-transport-e2e/`). Остался только 9 (удалённый демон по TCP) — спроектирован, не реализован.

## Context — зачем

Сегодня коммуникация с Telegram держится на **захвате чужого плагинного слота**: installer ставит
официальный `telegram@claude-plugins-official`, кладёт в его кэш свой бинарь `server-rs` и
**перезаписывает его `.mcp.json`**, подменяя `bun run server.ts` на `claudebase plugin serve`.
Дальше `claudebase run` запускает `claude --channels plugin:telegram@claude-plugins-official`, и
inbound-сообщения доезжают до сессии как MCP-нотификации `notifications/claude/channel`.

Подход хрупкий по построению, и **он уже сломан на этой машине, а не гипотетически**:

- официальный плагин обновился `0.0.6 → 0.0.7` (13 авг), в кэше `0.0.7` лежит **upstream `.mcp.json`
  с `bun run`**, `server-rs` отсутствует, `.mcp.json.upstream-backup` отсутствует — патч потерян
  молча, при первом же `plugin update`;
- канальная поверхность CC исторически нестабильна для нас: `docs/issues/002` (не срабатывает
  channel surface), `docs/issues/006` (доставка теряется на stale-бриджах, 7 живых процессов
  `claudebase plugin serve` при одном живом CC);
- сама фича каналов в CC 2.1.233 **гейтится серверным фиче-флагом Anthropic**
  (`tengu_harbor_ledger`), т.е. никакой сторонний плагин в дефолтный аллоулист не попадёт никогда —
  только `--dangerously-load-development-channels` или machine-wide managed-settings.

Решение оператора (2026-08-16), в два шага:

1. **Отказаться от плагинного/MCP-транспорта Telegram целиком** и перейти на транспорт, не зависящий
   ни от версии `claude`, ни от официального плагина, ни от фиче-флагов Anthropic:
   - **outbound** (агент → оператор): агент вызывает `claudebase telegram send --text "…"` через Bash →
     CLI проксирует в claudebase daemon по UDS → daemon шлёт в Telegram (эта половина уже
     существует внутри `chat_reply`, см. `src/daemon/server.rs:1085-1126`);
   - **inbound** (оператор → агент): Telegram → daemon (polling + ASR) → **`claudebase run` пишет
     текст прямо во ввод `claude`**, потому что `claudebase run` сам владеет PTY, в котором запущен
     `claude`.
2. **Не заводить собственный маркетплейс вовсе.** Он рассматривался как замена захвату чужого слота,
   но существовал бы ровно ради одного — доставить MCP-плагин с каналом. Канала больше нет →
   плагина нет → маркетплейс не нужен. Telegram-коммуникация и STT встроены в daemon, скиллы и
   агенты ставит standalone-installer.

Побочный, но крупный выигрыш: PTY-супервизор — это ещё и исправление корневых причин 1 и 3 из
`docs/issues/006` (уникальный `agent_id` на процесс + смерть подписки вместе с сессией).

## Целевая архитектура

```
                    ┌─────────────────────── claudebase daemon (standalone, user service)
                    │  TG long-poll  ──►  ASR (whisper)  ──►  chat.db  ──►  bus.publish(thread)
                    │  outbound TG queue ◄── chat_reply (UDS)
                    └──────────▲───────────────────────────────┬──────────
                               │ UDS (length-prefixed ipc)     │ UDS subscribe
                               │                               │
   ┌───────────────────────────┴────┐            ┌─────────────▼──────────────────────────┐
   │ claudebase telegram send --text │            │ claudebase run  (PTY-супервизор)       │
   │ (короткоживущий CLI-процесс,    │            │  • openpty; spawn `claude` на slave     │
   │  запускается агентом из Bash)   │            │  • real TTY ⇄ pty master (raw, SIGWINCH)│
   └────────────────▲────────────────┘            │  • подписка на треды; inbound → write   │
                    │ Bash tool                   │    в pty master (bracketed paste + CR)  │
   ┌────────────────┴─────────────────────────────┴─────────────────────────────────────┐
   │ claude (CLI, немодифицированный; НИКАКИХ --channels, плагинов, MCP-серверов)        │
   └────────────────────────────────────────────────────────────────────────────────────┘
```

Что исчезает: `--channels`, `notifications/claude/channel`, `claudebase plugin serve`, патч чужого
`.mcp.json`, `server-rs` в чужом кэше, `plugins/telegram-rs/`, зависимость от `tengu_harbor*`,
и сама идея маркетплейса.

Что ставит installer (всё standalone, один проход):

```
~/.claude/tools/claudebase/claudebase   бинарь (+ pdfium, e5-модель)
~/.claude/rules/                        cognitive-self-check
~/.claude/commands/                     knowledge-ingest, reflect, consolidate, update-claudebase
~/.claude/agents/                       reflection, consolidator
~/.claude/skills/claudebase-configure/  ← НОВОЕ (сейчас лежит в prompts/skills, никем не ставится)
~/.claude/skills/claudebase-access/     ← НОВОЕ
~/.claude/hooks/                        5 хуков + merge в settings.json
ffmpeg + whisper-cli                    STT-зависимости
daemon как user-service                 launchd / systemd-user
```

## Слайсы

Порядок такой, чтобы каждый слайс был отдельно проверяем, а **старый транспорт удалялся последним** —
до Слайса 6 остаётся возможность откатиться.

### Слайс 0 — спайк: инъекция во ввод `claude` через PTY (BLOCKING) — ✅ ВЫПОЛНЕН 2026-08-16, ГЕЙТ ПРОЙДЕН

**Результат:** инъекция работает end-to-end. `spikes/pty_inject/` (portable-pty 0.9), доказательства
в `docs/qa/evidence/pty-inject/`. Ключевые находки, которые становятся требованиями к Слайсам 2–3:

- **F-1** bracketed paste (`ESC[200~ … ESC[201~`) TUI понимает: маркеры не эхнулись, текст лёг в
  строку ввода целиком;
- **F-2** **submit обязан быть отдельной, отложенной записью**: `\r` в том же буфере, что и paste,
  не отправляет ничего; он же через 400 мс — отправляет (ответ модели получен). То есть «вставка» и
  «Enter» — два тайминговых события, а не один payload;
- **F-3** модальные диалоги съедают инъекцию, а «голый» CR их **подтверждает**: в первом прогоне CR
  ответил «Yes, use my browser» и открыл оператору браузер. Диалоги возникают и по ходу сессии, не
  только на старте, — значит проверка готовности нужна **перед каждой** инъекцией, а не однократно
  при запуске;
- **F-4** отсутствие TTY у самого супервизора не мешает inbound-доставке (все прогоны шли из
  агентского шелла без TTY);
- **F-5** вложенные сессии наследуют `CLAUDE_CODE_CHILD_SESSION` — артефакт стенда, в проде не
  воспроизводится.

Осталось непроверенным и уезжает в Слайс 3: инъекция **во время генерации**, инъекция **поверх
набираемой строки**, и Windows/ConPTY (риск R-3).

Ниже — исходная постановка слайса (сохранена как контекст).

Единственный по-настоящему неизвестный кусок. Мини-программа в `spikes/pty_inject/` (конвенция репо —
там уже был `spikes/ipc_concurrent_accept/`):

1. `openpty` → spawn `claude` со slave как stdin/stdout/stderr;
2. реальный терминал в raw-mode, двусторонний проксинг + `SIGWINCH` → `TIOCSWINSZ`;
3. через N секунд после старта записать в master тестовый текст и `\r`.

Done-condition спайка — не «работает/не работает», а измеренные ответы на:

- принимает ли TUI **bracketed paste** (`ESC[200~ … ESC[201~`), как рендерит многострочный блок;
- нужен ли `\r` или `\n` для сабмита; не сабмитит ли bracketed-paste сам по себе;
- что происходит при инъекции **во время генерации ответа** (очередь ввода CC) и **во время того,
  как оператор печатает сам** (порча строки — вероятна, отсюда «тихое окно» в Слайсе 3);
- поведение, когда у самого `claudebase run` нет TTY (запуск из systemd/скрипта).

Выход: `docs/qa/evidence/pty-inject/` + зафиксированный формат инъекции. **Если TUI не принимает
инъекцию — план пересматривается целиком**, поэтому слайс блокирующий.

Крейт: `portable-pty` (wezterm) — Unix PTY и Windows ConPTY одним API; альтернативы (`pty-process`,
ручной `nix::pty::openpty` + `libc`) не покрывают Windows, а релизная матрица включает `windows-x64`.
`TIOCSTI` (инъекция в чужой терминал) **исключён**: на этой машине `dev.tty.legacy_tiocsti = 0`,
в современных ядрах он выключен по умолчанию — то есть это ровно тот хрупкий путь, от которого уходим.

### Слайс 1 — ✅ ВЫПОЛНЕН — outbound: `claudebase telegram send` + `claudebase agent chat`

Реализовано: `src/daemon/client.rs` (короткоживущий UDS-клиент), `src/telegram_cli.rs`,
`src/agent_cli.rs`, колонка `session_token` в `agent_registry` + токен-аутентификация отправителя
в `agent_send`. Живая проверка: агент внутри сессии сам вызвал `claudebase telegram send --text`
без аргументов адресата; межагентская отправка отработала с отказом на неоднозначном имени и на
неверном токене (`docs/qa/evidence/pty-transport-e2e/` run 1 и run 4).

Постановка (сохранена):

- новый модуль UDS-клиента (`src/daemon/client.rs`), переиспользует `ipc::{read_frame, write_frame}`;
  сейчас единственный клиент — `src/plugin/bridge.rs`, логика подключения/ретраев вкопана в него;
- поверхность:
  ```
  claudebase telegram send --text "…"          # адресат резолвится сам
  claudebase telegram send --stdin             # многострочный текст без ада с кавычками
  claudebase telegram send --text "…" --thread telegram:<chat_id>   # явный override
  claudebase telegram status                   # кому сейчас привязана эта сессия
  ```
- **резолв адресата без аргументов** — ключевое для эргономики: агент не должен знать `chat_id`.
  Порядок: `--thread` → routing-key текущего агента (`agent_registry::bind_routing_key`,
  `src/daemon/agent_registry.rs:839`, ставится при `/switch` в TG) → единственный известный
  telegram-тред → иначе внятная ошибка со списком доступных тредов;
- идентичность процесса берётся из env `CLAUDEBASE_AGENT_ID`, который проставляет супервизор
  (Слайс 2) в окружение `claude`, — Bash-вызовы наследуют его автоматически;
- под капотом — тот же `chat_reply`: персист в `chat.db` + `enqueue_outbound_tg_tracked`
  (`server.rs:1085-1126`). **Никакой новой логики отправки.**
- тест: `tests/cli_telegram_send_test.rs` против поднятого в тесте daemon (шаблон —
  `tests/chat_tools_e2e_test.rs`).

**Межагентская коммуникация — та же CLI-поверхность** (решение оператора 2026-08-16, снимает OQ-1):

```
claudebase agent chat --text "…" --agent <name>        # по имени: резолв в newest-alive agent_id
claudebase agent chat --text "…" --agent-id <uuid>     # по точному id
claudebase agent chat --stdin --agent <name>
```

- под капотом — существующий `agent_send` (`server.rs:719`, схема `to_agent_id` + `content`,
  DND-очередь с `{queued: true, delivered_when}` уже реализована);
- резолв `--agent <name>` → newest-alive `agent_id` через существующий `agent_list_alive`;
  неоднозначность (несколько живых с тем же именем) — ошибка со списком, а не молчаливый выбор;
- **привязка идентичности отправителя** — единственное место, где нужен новый механизм. Сегодня
  `agent_send` резолвит отправителя server-side из `connection_id` зарегистрированной сессии
  (FR-C2C-4.6, анти-импersonation). Короткоживущий CLI-процесс приходит по **своему** соединению и
  такой идентичности не имеет. Решение: супервизор при регистрации получает от daemon
  **per-session token**, кладёт его в env ребёнка (`CLAUDEBASE_SESSION_TOKEN`); CLI предъявляет
  токен, daemon резолвит `token → agent_id`. Это сохраняет запрет на импersonation в пределах
  машины: подделать отправителя может только тот, кто уже прочитал env чужого процесса.
  Альтернатива «доверять `--from`» отвергнута — она обнуляет FR-C2C-4.6;
- тест: `tests/cli_agent_chat_test.rs` — резолв по имени, отказ при неоднозначности, отказ без
  токена, DND-очередь.

Обе команды объединяет один UDS-клиент и один способ аутентификации — разными остаются только
целевой инструмент daemon (`chat_reply` vs `agent_send`) и резолв адресата.

### Слайс 3 — ✅ ВЫПОЛНЕН — политика инъекции (риски проверены на стенде, затем реализовано и проверено вживую)

По просьбе оператора риски Слайса 3 сняты **до** написания продового кода — стенд умеет
скриптовать и сторону оператора, поэтому «набор человека» проверяется без человека.
Доказательства: `docs/qa/evidence/pty-inject/` (сценарии `busy`, `typing`, `multiline`).

| Риск | Проверка | Итог |
|---|---|---|
| инъекция во время генерации | `--scenario busy` | ✅ **встаёт в очередь**, обрабатывается сразу после текущего ответа, ничего не теряется |
| многострочный блок | `--scenario multiline` | ✅ **атомарен** — 3 строки = одно сообщение, один ответ |
| инъекция поверх набранной строки | `--scenario typing` | ❌ **тихая склейка**: черновик оператора слился с входящим и ушёл одним промптом |
| модалка во время сессии | побочно в `busy` (1-я попытка) | ❌ сообщение **потеряно целиком** (0 вхождений в транскрипте), CR провёл мастер настройки дальше |

Реализация: `src/supervisor/draft.rs` (точный учёт черновика), `src/supervisor/screen.rs`
(детектор модалок по сигнатурам вывода), `src/supervisor/inject.rs` (очередь, склейка пачки,
дедуп по `message_id`, paste + отложенный submit, повторная проверка модалки ПЕРЕД Enter).
Живая проверка под настоящим TTY: сообщение прождало занятую строку ~11 с и вошло через 470 мс
после того, как оператор отправил свою (`docs/qa/evidence/pty-transport-e2e/` run 3).

**F-6 — склейка с черновиком** делает «тихое окно» обязательным, но, что важнее, показывает, что
таймерная эвристика тут не нужна вовсе: супервизор — единственный путь клавиатуры оператора,
поэтому он знает состояние строки **точно**:

- печатный байт / вставка от оператора → черновик грязный;
- `\r`/`\n`, `Ctrl-C` (0x03), `Ctrl-U` (0x15) → черновик чист;
- backspace (0x7f) → декремент, чист на нуле;
- стрелки / history recall → считать грязным (текст появляется без печатного символа).

Пока грязно — входящие копятся и склеиваются; на переходе в «чисто» — флаш. Это детерминированный
учёт, а не догадка, и он же снимает необходимость угадывать паузы.

**F-3 (подтверждён дважды, серьёзнее чем думали)** — модалка не просто мешает: сообщение
**теряется без следа**, а submit-клавиша управляет чужим мастером. Прод-форма запуска
(`--dangerously-skip-permissions`, который `claudebase run` и так ставит по умолчанию) убрала
конкретную модалку auto-mode, но не отменяет класс проблемы. Требования: детектор модалок перед
каждой инъекцией + очередь неотправленного (а не best-effort запись).

Ниже — исходная постановка слайса.

### Слайс 3 (постановка) — политика инъекции

- **формат**: один блок с явной рамкой и метаданными (from, thread, message_id, ts). Форма берётся
  из уже существующего рендера (`src/daemon/chat.rs:build_channel_notification`, контракт описан
  в `src/plugin/mcp.rs:185`), чтобы не переписывать промпты и скиллы;
- **тихое окно**: не инъектить, пока оператор печатал последние N мс; копить в очереди;
- **готовность перед КАЖДОЙ инъекцией** (следствие F-3): не писать, пока в потоке вывода ребёнка
  видны признаки модального диалога («Enter to confirm», «❯ 1.»); иначе submit-клавиша подтвердит
  чужой выбор. Это не стартовая проверка, а состояние, отслеживаемое постоянно;
- **submit отдельной записью** через паузу (F-2), а не в одном буфере с paste;
- **дедуп**: по `message_id` — реконнект к daemon не должен вызывать повторную вставку;
- **backpressure**: поток сообщений склеивается в один блок, а не N вставок подряд;
- **правило ответа**: первый инъекшен в сессии несёт одну строку-инструкцию «отвечать через
  `claudebase telegram send --text "…"`»; дальше — только рамка.

### Слайс 8 — ✅ ВЫПОЛНЕН — реестр Telegram-ботов в SQLite

**Проблема, которую он закрывает.** Токен жил в двух файлах с разными форматами и разными
владельцами: `~/.claude/channels/claudebase/.env` (пишет скилл configure) и
`~/.config/claudebase/secrets.toml` (легаси-путь демона). `docs/issues/004` — ровно про это
рассогласование: оператор настраивает одно, демон читает другое.

**Решение.** Таблица `telegram_bots` в `chat.db` — БД, которой демон уже владеет, которая уже
создаётся с правами 0600 и открывается на каждом запросе. Один владелец на одну сущность, и
мульти-бот получается бесплатно (его хочет план флота v0.9). Файловые источники остаются
фолбэками в прежнем относительном порядке, так что существующие установки не требуют
переконфигурации: **реестр → `.env` → `secrets.toml`**.

Поверхность:

```
claudebase telegram addbot <token> [--label "…"]   # проверяет через getMe, затем пишет
claudebase telegram bots                            # список; секреты не печатаются никогда
```

Решения, которые стоит знать:

- **`getMe` вызывается ДО записи.** Токен проверяется на живость, а его `bot_id`/`username`
  приходят от самого Telegram. Это же делает повторный `addbot` того же бота **ротацией токена**, а
  не дубликатом — то есть штатным действием после утечки, а не поводом чистить БД руками.
- **Ключ таблицы — `bot_id` от Telegram**, не автоинкремент. Отсюда идемпотентность.
- **Токен хранится в открытом виде**, как и раньше в `.env`/`secrets.toml`. Это не понижение
  уровня: демон обязан предъявлять Telegram литеральный токен на каждом вызове, поэтому любое
  обратимое кодирование здесь было бы замком с ключом в скважине. Что БД добавляет поверх файлов —
  единственный владелец, 0600 по построению и отсутствие риска, что редактор оставит рядом
  world-readable копию. Всё, что форматирует токен для человека, идёт через `mask()`.
- **Ошибки скрабятся.** `reqwest` вставляет URL запроса (а он несёт токен) в свой Display —
  строка ошибки как раз то, что люди вставляют в issue.

Проверено на живом токене: `stored @<bot> (id <bot_id>, token <bot_id>:AAH…XXX)`,
после рестарта демон поднял `telegram long-poll spawned` без ошибок авторизации. 6 юнит-тестов
(форма токена, отказ до сетевого вызова, первый бот = дефолтный, ротация без дубля, пустой реестр,
маска не раскрывает секрет).

### Слайс 12 — ✅ ВЫПОЛНЕН — то, что вскрыла живая эксплуатация

Пять дефектов, найденных не тестами, а работой оператора с реальным ботом. Каждый — тихий:
транспорт выглядел исправным и молча делал не то.

**F-9. Гейт закрывался мусором терминала.** Claude Code включает focus-reporting (DEC 1004) и
mouse-tracking (1000/1002/1003/1006) — прочитано из живого транскрипта. Значит терминал шлёт
escape-последовательности при каждом движении мыши и переключении окна, а трекер черновика считал
любую из них признаком «на строке появился текст». Оператор уходил в Telegram и возвращался — гейт
закрывался навсегда. Теперь последовательности классифицируются: Up/Down и вставка грязнят,
focus/mouse/перемещение курсора — нет (`src/supervisor/draft.rs::classify_escape_sequence`).
Диагностика при заторе печатает `chars/recalled/last_dirty_input`, то есть ЧТО именно держит.

**F-10. Бэклог вываливался целиком.** `chat_subscribe` отдаёт все недоставленные сообщения треда
(в `drain_backlog` нет ни `LIMIT`, ни окна) и помечает их доставленными. Добавленная в Слайсе 3
доставка бэклога не ограничивала ничего, поэтому накопившаяся переписка падала в ввод одним куском.
Теперь: не старше 10 минут, не больше 5 сообщений, оставляются свежие, отброшенное логируется —
молча терять нельзя, они уже помечены доставленными на стороне демона.

**F-11. Сообщения приходили не в ту сессию.** Супервизор подписывался на все telegram-треды из
`access.json` и `chat.db`, поэтому сессия в постороннем проекте получала чужой чат — и, что хуже,
ЗАБИРАЛА его бэклог. Подписка сузилась до: собственный инбокс, чаты, привязанные `/switch` к этой
сессии, и явные `--subscribe`. Принадлежность перепроверяется на каждом сообщении, потому что
отписки в протоколе нет и `/switch` может увести чат. **Следствие, принятое сознательно:** без
`/switch` сообщения не приходят никому — прежнее «слышат все» и было источником путаницы.

**F-12. `state` в реестре врал.** Строка остаётся `alive`, пока демон не заметит EOF или не
перезапустится, поэтому `/switch` предлагал четыре одинаковые кнопки `planner` для давно умерших
сессий. Колонки `host`/`pid`/`cwd` существовали с миграции routing, но их никто не заполнял.
Теперь супервизор передаёт их при регистрации; `list_online` сверяет `state` с таблицей процессов
(`kill(pid,0)`, причём `EPERM` — это «жив», иначе чужой процесс считался бы мёртвым — поймано
тестом); `/agents`, `/switch` и `claudebase agent list` используют её. При регистрации хоронятся
строки того же слота (ник + cwd + host), чей процесс мёртв — это и есть дедупликация. Две реально
работающие сессии в одном каталоге остаются обе. Ник уникализируется: `planner`, `planner-2`, … —
иначе кнопки неразличимы.

**F-13. Логи супервизора лезли в ввод TUI.** Уровень по умолчанию был `info`, а stderr супервизора —
это терминал оператора, поэтому JSON появлялся прямо в поле ввода Claude Code. Логи ушли в
`~/.claude/logs/claudebase-run-<pid>.log`; `CLAUDEBASE_LOG_STDERR=1` возвращает прежнее поведение
для отладки самого супервизора вне TUI. Успешный старт больше не печатает ничего.

**F-14. Сообщение из телеги приходило с префиксом `[agent-to-agent:codefath]`.** У демона три
разных билдера уведомлений, и они не согласны, где лежит тред. `build_channel_notification_telegram`
кладёт в `meta.chat_id` голый числовой id чата строкой (`"434566766"`) и не заполняет `meta.thread`;
`build_channel_notification_agent_to_agent` кладёт в тот же `meta.chat_id` имя треда `agent:<id>`;
`build_channel_notification` (посты и реплаи) использует `meta.thread` — и только там префикс
`telegram:` действительно есть. Подписчик классифицировал источник по `thread.starts_with("telegram:")`,
что для настоящих телеграм-сообщений не срабатывало никогда: ветка падала в agent-to-agent, а ник
брался из `nick_for("codefather_dev")` с обрезкой до 8 символов. Отсюда же ломался ответ —
`claudebase agent send --agent_nick codefath` не находил живого агента. Классификация вынесена в
`classify()` с явным порядком: префикс в `meta.thread` → `agent:` в `meta.chat_id` → числовой
`chat_id` (его порождает только телега, нормализуется в `telegram:<id>`) → иначе peer. Тесты строят
кадры **настоящими** билдерами, а не фикстурами: расхождение с реальным продюсером — это и был баг.

**F-15. Ник отправителя иногда подменялся его agent_id.** Оператор поймал в соседнем окне
`[agent-to-agent:d1eb9528]` — первые 8 символов id вместо ника, — причём соседнее сообщение от того же
отправителя пришло с правильным `planner`. Две независимые причины, обе воспроизведены тестом.

Первая: `open_chat_db` — единственная база проекта без `busy_timeout` и без WAL (`store.rs:122`
ставит оба для базы знаний). SQLite по умолчанию не ждёт освобождения блокировки, а немедленно
отдаёт `SQLITE_BUSY`. Хуже того, `ensure_chat_db_schema` гоняет `BEGIN; CREATE TABLE …` при **каждом**
открытии, так что резолв ника — это писатель, конкурирующий с демоном, который в тот же момент
сохраняет ровно это сообщение. `.ok()` проглатывал ошибку, и «не смог прочитать» становилось
неотличимо от «такого агента нет». Лечится `busy_timeout(5s)` + WAL на `open_chat_db` и отдельным
`open_chat_db_readonly()` для горячих чтений, который не открывает транзакцию записи вовсе.

Вторая, независимая: фоллбэк обрезал id до 8 символов. `resolve_target` принимает **полный**
agent_id, но никогда не префикс, поэтому получатель не мог ответить на такую метку — тот же дефект,
что сделал `codefath` недоставляемым в F-14. Фоллбэк теперь — полный id, а неудача чтения логируется
`warn` и отличима от честного «отправитель неизвестен».

### Слайс 14 — память ника за каталогом проекта

Оператор попросил, чтобы сессия сама придумывала себе ник на старте вместо дефолтного имени проекта.
Прямая реализация сломала бы Слайс 13: `chat_bindings` ключуются **ником**, и ник, выдуманный заново
при каждом запуске, не даёт `restore_bindings_for` ничего восстановить — возвращается ровно та
проблема, ради которой Слайс 13 и делался. Поэтому имя придумывается один раз и запоминается.

`nick_memory(host, cwd, nick, updated_at)` — ключ (host, cwd), а не agent_id: каждый рестарт создаёт
новый agent_id, поэтому всё, что ключуется им, умирает вместе с процессом (та же логика, что увела
привязки с строки реестра). Запись — только при явном `agent rename`; выведенное из имени каталога
не запоминается, иначе «выбранное» стало бы неотличимо от «выпало из пути», а именно это различие
нужно хуку. `identity::derive` вспоминает имя, если оно свободно; занятость проверяется через
`process_is_live`, чтобы упавшая сессия не удерживала имя навсегда.

`claudebase agent whoami` печатает ник, id и `origin: chosen|auto` — read-only и без демона, потому
что хук на старте сессии не должен висеть на занятой базе. SessionStart-хук добавляет просьбу
выбрать имя **только** при `origin: auto`, и после переименования замолкает.

Тесты: 249 в библиотеке (новые — 6 на живость и дедупликацию, 4 на границы бэклога, 6 на
классификацию escape-последовательностей, 4 на классификацию источника уведомления).

### Слайс 9 — ПРОЕКТ (не реализован) — удалённый демон по TCP

Цель оператора: `claudebase daemon baseurl "http://192.168.31.170:<port>"` — держать демон на
отдельной машине в локальной сети и подключаться к нему с нескольких машин.

**Транспортная часть тривиальна, и это ловушка.** Кадрирование (`ipc::read_frame/write_frame`) уже
абстрактно над `AsyncRead`/`AsyncWrite`, так что TCP добавляется enum-обёрткой
`Endpoint::{Local(PathBuf), Remote(SocketAddr)}` вокруг `interprocess::Stream` / `TcpStream`.
Настоящая работа — в двух местах, и оба обязательны:

**1. Безопасность. Сейчас защита — это права на файл сокета.** UDS лежит в `/run/user/1000/` с
режимом 0700: «дотянуться до сокета» и «быть этим пользователем» — одно и то же. TCP в локалке
снимает это полностью, а поверхность демона включает `chat_reply` (пишет оператору в Telegram),
`agent_send`, `chat_list` (вся история переписки) и БД с токенами ботов. Выставить это без
аутентификации — значит отдать любому в сети право писать от вашего имени в ваш Telegram.
Минимум для слайса:

- **PSK-аутентификация**: `auth_token` в конфиге демона; клиент предъявляет его первым кадром,
  демон отвечает `-32600` и рвёт соединение при несовпадении. Токен генерируется при
  `daemon listen --generate-token`, а не придумывается оператором.
- **Bind по умолчанию `127.0.0.1`**, выставление наружу — только явным `--bind 0.0.0.0:<port>` с
  громким предупреждением в лог и в вывод команды.
- **TLS (rustls) — рекомендуемый, но опциональный.** По проводу идёт контент сообщений; токены
  ботов не ходят, но переписка оператора — да. Альтернатива для тех, кто не хочет возиться с
  сертификатами: SSH-туннель и bind на localhost. Это стоит явно написать в доке, а не оставлять
  на догадку.
- Rate-limit на неудачные аутентификации, чтобы PSK нельзя было брутфорсить с той же локалки.

**2. Клиент читает `chat.db` напрямую — и на удалённой машине её нет.** Это главный блокер, а не
безопасность. Прямые чтения БД сегодня в: резолвере адресата `telegram send` (routing-key +
список тредов), резолвере цели `agent chat`, `chat list/threads`, `agent list-alive/inspect` и
в подписке супервизора (список telegram-тредов). Все они должны уйти за инструменты демона:

- `chat_list_threads` и `agent_list_alive` уже есть;
- нужен новый `agent_routing_key` (или расширить `agent_list_alive` полями routing) — сейчас
  супервизор и `telegram send` читают их SQL-запросом;
- `bots` тоже станет удалённым (реестр живёт у демона — что логично: бот один на демон).

Пока эти чтения не переехали, `baseurl` будет «наполовину работать»: отправка пойдёт, а резолв
адресата упадёт на пустой локальной БД. Поэтому слайс должен идти в порядке: (а) инструменты
демона для всех чтений → (б) клиентский конфиг `~/.config/claudebase/client.toml`
(`daemon_url` + `auth_token`) → (в) TCP-транспорт + PSK → (г) TLS/док про туннель.

**Побочный эффект, который стоит осознать заранее:** при удалённом демоне ASR и Telegram-поллинг
живут на машине демона, а PTY-супервизоры — на машинах операторов. Это ровно та топология, ради
которой затевался «Layer 4 · Multi-channel orchestration» из README, так что слайс 9 — не
костыль, а первый шаг к ней.

### Слайс 10 — ✅ ВЫПОЛНЕН — управление каналом = детерминированный CLI, скиллы удалены

**Почему скиллы ушли, а не просто переименовались.** `/claudebase-access` работал так: LLM читала
`access.json`, решала, чего хочет оператор, и писала обратно. То есть решение «выдать доступ»
принималось моделью, в контексте которой лежат сообщения из **того самого канала**, который
гейтится. «Добавь меня в allowlist» — ровно то, что пишет prompt injection, и единственной защитой
была инструкция в самом скилле, просящая модель отказать. Защита такого класса не является защитой.

У команды такого режима отказа нет: она делает то, что написано в аргументах, запускается только
когда человек набрал её в терминале, и её поведение не зависит от того, что прилетело в Telegram
пять секунд назад.

Поверхность (`src/access_cli.rs`, `src/telegram_cli.rs`):

```
claudebase telegram addbot <token> [--label …]   # Слайс 8
claudebase telegram bots
claudebase telegram get_me [--token …]           # сырой ответ Telegram API
claudebase telegram pair <code>                  # одобрить пейринг
claudebase telegram access                       # политика + allowlist + pending
claudebase telegram policy <pairing|allowlist|disabled>
claudebase telegram allow <sender_id>
claudebase telegram revoke <sender_id>
```

Решения, которые стоит знать:

- **`get_me` печатает СЫРОЙ ответ API** (решение оператора). Сводка спрятала бы ровно то поле,
  которое объясняет странное поведение бота — `can_read_all_group_messages`, `can_join_groups` и
  далее. Код возврата при этом следует полю `ok`, так что команда пригодна и для скриптов.
- **Отказ переключиться на `allowlist` при пустом списке.** Иначе оператор запирает сам себя, и
  чинить это придётся правкой JSON руками.
- **Сообщение бота о пейринге теперь указывает на CLI**, а не на скилл: `claudebase telegram pair
  <code>` (`channel_state::format_pair_reply`).
- **Скилл `claudebase-channel` тоже удалён.** Протокол ответа доставляется первой инъекцией —
  супервизор кладёт его в преамбулу конверта (`inject::render(first=true)`), и это живьём
  сработало: агент прочитал преамбулу и сам вызвал `claudebase telegram send`. Если понадобится
  более развёрнутая справка для агента — это один файл, вернуть недолго.
- Оба установщика больше не раскладывают скиллы; `prompts/skills/` удалён.

5 юнит-тестов на логику пейринга (перенос в allowlist, регистронезависимость кода, отказ по
истечении срока, неизвестный код ничего не выдаёт и не съедает настоящий, повторный пейринг не
дублирует отправителя).

### Слайс 11 — ✅ ВЫПОЛНЕН — контракт сообщений: префиксы вместо конверта, и сквозная зачистка доков

Решение оператора 2026-08-16. Входящие приходят в ввод сессии префиксной строкой:

```text
[telegram_message]: текст оператора
[agent-to-agent:<nick>]: текст соседней сессии
```

Почему это лучше прежнего `<channel …>`: тот конверт был унаследован от канальной поверхности
Claude Code — ровно того механизма, от которого этот транспорт ушёл. Тащить дальше его разметку
значило бы шуметь в вводе модели ради совместимости с тем, чего больше нет. Префикс делает то же
самое двумя словами: помечает строку как СООБЩЕНИЕ, а не ввод оператора, и называет отправителя.

Ник, а не uuid: адресовать ответ по `agent_id` человек не может, и модель тоже. `subscribe_client`
резолвит `agent_id → agent_name` из реестра, а `sanitize_nick` вырезает всё, кроме
`[a-zA-Z0-9._-]`, — иначе сессия, назвавшаяся `x]: [telegram_message`, подделала бы канал
оператора (есть тест).

Поверхность межагентской связи переименована под контракт оператора:

```
claudebase agent send "текст" --agent_nick <nick>   # было: agent chat --text --agent
claudebase agent send "текст" --agent_id <id>       # когда ники совпадают
claudebase agent list [--all] [--json]              # ник, id, online/offline, чем занят
claudebase agent describe "…"                       # было: MCP-инструмент agent_describe
```

`agent describe` получил ту же токен-аутентификацию, что и `send`: короткоживущий CLI доказывает,
за какую сессию говорит, вместо того чтобы даймон верил переданному id.

**Доки и хуки.** Инструкции приходят до первого сообщения, а не по требованию: новый
SessionStart-хук `claudebase-channel-contract` (sh + ps1, ASCII — `docs/issues/003` про BOM) кладёт
контракт в контекст каждой сессии. Хук `agent-routing-reminder` переписан с MCP-инструментов на
CLI, `feature-describe` — на `claudebase agent describe`. README: секции Telegram и multi-agent
переписаны целиком. Исторические артефакты (PRD §17, use-cases, QA, планы v0.6/v0.9) не
переписывались — переписать запись о прошлой фиче значит подделать историю; вместо этого у них
баннер «superseded, вот действующий контракт». `plugins/telegram-rs/README.md` помечен как мёртвый
код до Слайса 6.

Живая проверка: две сессии, оба формата в транскрипте (`[telegram_message]:` и
`[agent-to-agent:planner]:`), `<channel` не встречается ни разу.

## План Б — запасные транспорты (не отменяют PTY, страхуют его)

Решение оператора 2026-08-16: основным остаётся PTY, но два официальных пути фиксируются как
запасные — на случай, если PTY где-то не заведётся (реалистично: Windows/ConPTY, риск R-3) или
понадобится безголовый режим «агент работает без человека за терминалом».

### Б-1 — `claude -p --input-format stream-json --output-format stream-json`

**Проверено эмпирически 2026-08-16** (стенд `spikes/pty_inject/`-независимый, скрипт в
`docs/qa/evidence/stream-json/`): один процесс `claude`, два сообщения через 12 с — **оба
обработаны в одной сессии**, `session_id` общий, контекст сохранён (`cache_read_input_tokens`
16 016 → 41 092), ответы `альфа` и `браво`.

Что этот режим даёт даром — ровно те проблемы, которые PTY пришлось решать руками:

| Проблема PTY | Б-1 |
|---|---|
| F-2 отложенный submit, подбор таймингов | нет: сообщение — одна JSON-строка |
| F-3 модалки съедают сообщение, CR листает мастер | нет модалок вообще |
| F-6 склейка с черновиком оператора | нет черновика — нет склейки |
| нет подтверждения доставки | `--replay-user-messages` возвращает входящее с `isReplay: true` |
| парсинг ANSI для детекта состояния | структурированные события `system/init`, `assistant`, результат с `usage`/`cost` |

Чего он стоит: **`-p` не имеет TUI**. Оператор не может сидеть в этой сессии, нет слэш-команд,
нет диалогов разрешений, нет привычного вывода. Это не «PTY, только лучше» — это другой продукт:
безголовый воркер, у которого единственный канал общения — Telegram. Поэтому Б-1 — не замена
`claudebase run`, а параллельный режим (условно `claudebase run --headless`), уместный там, где
человека за клавиатурой нет.

### Б-2 — Claude Agent SDK

Официальный SDK для построения собственного клиента поверх той же модели и тулинга. По сути —
поддерживаемая обёртка над тем же потоковым протоколом, что и Б-1, но с версионируемым API вместо
CLI-флагов. Уместен, если claudebase когда-нибудь захочет собственный интерфейс, а не терминал
Claude Code.

### Что НЕ является планом Б

Форк «утёкших» исходников Claude Code. Продукт закрытый: публично лежат issues/доки/примеры
плагинов, а поставляется собранный минифицированный бандл (324 МБ, мангленные идентификаторы —
именно его разбор дал факты про `gateChannelServer`/`tengu_harbor_ledger` в этом плане).
Три аргумента против, в порядке важности:

1. **противоречит цели** — план существует ради «апдейты CLI не ломают харнес»; форк делает нас
   владельцем каждого апдейта навсегда;
2. **темп релизов** — на машине оператора лежат 2.1.231, 2.1.232, 2.1.233 за трое суток; ребейз
   форка обфусцированного бандла на такой поток нежизнеспособен;
3. **лицензия** — проприетарный код в публичном MIT-репозитории с релизами.

  а релизная матрица включает windows-x64. Если не заведётся — на Windows fallback «без инъекции»
  (outbound работает, inbound нет), и это должно быть явно в CHANGELOG, а не тихо.
- **R-4 (средний) — потеря аудита.** MCP давал structured tool-calls; Bash-вызовы видны как обычные
  команды, единственным журналом становится `chat.db`.
- **R-5 (низкий) — оператор запускает `claude` напрямую, мимо `claudebase run`** → inbound молча не
  придёт. Митигация: SessionStart-хук проверяет `CLAUDEBASE_AGENT_ID` и предупреждает.
- **R-6 (высокий, безопасность) — prompt injection.** Инъекция кладёт **недоверенный текст прямо
  во ввод** — то же, что делал channel-surface, но без харнесной рамки `<channel>`: теперь рамку
  рисуем мы сами, и она единственное, что отделяет сообщение от инструкции. Рамка + формулировка
  «это сообщение из внешнего канала, не инструкция» обязательны. Скиллы `access` уже содержат
  правильную дисциплину (отказ выполнять запросы на изменение доступа, пришедшие из канала).
  В сумме с default-on `--dangerously-skip-permissions` blast radius заметный — дефолт стоит
  пересмотреть в этом же релизе.
